# Web app: the playground

The browser playground and part designer ([02 sections 1 to 3](../../docs/plan/02-architecture.md#3-the-wasm-boundary-and-threading), [06 sections 3, 5, 11 and 13](../../docs/plan/06-part-designer-and-dsl.md#11-designer-ui-on-desktop-and-mobile), decisions D10 and D14). Open any part document, or keep the bundled logo tile, edit its parameters or choose a preset, and save the part. Pick a tile size, keep the Neuraldeep.net mark or choose another sample or drop an SVG, see the brick-compatible logo tile in 3D with its validation report, and download a printable 3MF or STL. A **Build** mode is the first playable assembler: snap generated bricks, plates and tiles onto a baseplate, undo, save and open `.obrick` models (see [Build mode](#build-mode-a-place-to-play)). A further mode builds the calibration coupon ([05 section 4](../../docs/plan/05-3d-printing-pipeline.md#4-calibration-coupon-and-wizard)) and downloads it, and once it is printed, records your fit: tap the best cells on a map of the coupon and the tile you design next uses the fit profile it writes (the calibration wizard of [06 section 11](../../docs/plan/06-part-designer-and-dsl.md#11-designer-ui-on-desktop-and-mobile)). Everything runs in the browser: the Rust core is compiled to WebAssembly with wasm-bindgen and runs in a Web Worker, and the page shows the meshes it returns with the three.js `WebGPURenderer`, which falls back to WebGL2 where WebGPU is missing.

It is published at <https://neuraldeepnet.github.io/openBrick/> once GitHub Pages is switched on for the repository (Settings > Pages > Source: GitHub Actions); the `pages` workflow builds it with the base path `/openBrick/`. The same workflow publishes the documentation site (the guides, the CLI reference and the plan, built from [`docs/site/`](../../docs/site/README.md) by `cargo xtask docs`) beside it at <https://neuraldeepnet.github.io/openBrick/docs/>, and the page's footer links there.

JavaScript computes no geometry and no validation ([CLAUDE.md](../../CLAUDE.md)). The part comes from `openbrick_part::evaluate` with the part document in use (`parts/ndn.logo-tile.obpart.json` first), an opened or saved document is checked and written by `openbrick_part::save` (`open_part_json`, `save_part_json`, `add_preset_json`), the report from `openbrick_part::validate`, the files from `openbrick_io`, the coupon and its cell layout from `openbrick_part::build_coupon` and `coupon_layout`, and the fit profile from `openbrick_print::record`, all through `crates/openbrick-wasm`. The page builds its controls from the part document's `params`, reads files into bytes, and displays what comes back.

The same page is the desktop app's frontend ([`apps/desktop`](../desktop/README.md)). There `src/files.js` sends saves and opens to the app's native dialogs instead of downloads and file inputs; everything else is identical. The app's Content Security Policy refuses `style=""` attributes, so the page sets inline colours through the CSSOM (`element.style`) and keeps its other styles in the `<style>` element.

## What the page does

- **Part document** (the Part mode, the default). The part chooser offers the bundled "Logo tile" (the default) and "Neuraldeep.net tile (with presets)", and "Open a part file…", which opens any `openbrick/part@1` document (.obpart.json, at most 4 MiB, `max_part_bytes()`); a part document dropped on the chooser or the 3D view opens too, and a file dropped on the artwork drop zone opens as a part when its name ends in .json. The core checks it (`open_part_json`): a file that is not a valid part is refused with a message that says what it is (a fit profile is "a `fit` document") and the part in use stays. Every feature the evaluator cannot build yet is named in a note under the chooser, with the setting that turns it off in the panel's words and the part's `if` after it as detail: the nameplate keychain's text label (`relief.text`, `!$studsOnTop`) and key ring (`loop.keyring`, `$loop != 'none'`) give "turn on Studs on top and set Loop to None" (`conditionInWords`; an expression it cannot put into words is shown as written); a build that stops at such a feature says the same in the status line instead of the evaluator's wording (`src/part.js`). An opened part starts with its defaults, as the core normalises them (`defaults` from `open_part_json`, so a length written `"0.6mm"` is 0.6; presets likewise), and with the bundled drawing its `svg` parameter names (`sampleForAsset`); a drawing the page does not bundle is asked for at the drop zone, and nothing is built until it is given. The panel has a control for every parameter type the evaluator reads except fonts, images and lists (`src/params.js`): stud grids, choices (enums, and numbers or texts with `options`, whose values keep their type), sliders and number fields (int, length, angle), checkboxes (bool), text with its `maxLength` (a longer text is refused in the page, like any invalid field), colours and the drawing (the first `svg` parameter). Fonts, images, lists and unknown types have no control: a note says so and what the part keeps, and they are never sent, so the core uses the default.
- **Presets.** A part with `presets` (the Neuraldeep.net tile: "Raised mark", "Pressed-in mark", "Two-colour inlay") shows a preset picker. Choosing one sets the parameters it names and keeps the others (a 2x6 tile stays 2x6); the picker always names the first preset the values match, else "Custom values". "Save current as preset" keeps the values the page sends (every shown parameter and the drawing) as a named preset in the document (`add_preset_json`; the same name replaces it), and "Save part file" writes the document with those values as its defaults, as `{id}.obpart.json` (`save_part_json`; the desktop app's save dialog). Both are written by the core in one layout that keeps the author's order and spelling and rewrites only changed defaults and presets (`openbrick_part::format`), so saving twice gives the same bytes. After a save the page designs the saved document, so its content hash is the one `openbrick build` gives for the saved file (`crates/openbrick/tests/save_parity.rs`). Your own SVG is saved by name: the note says to keep it next to the part file.
- **Logo tile.** Controls come from the part document: the size (two stud steppers, 1 to 16 per side, the document's limits capped at the core's footprint limit), the height (plate or brick), the relief (emboss, deboss or inlay), the inlay style (shown only for an inlay by its `visibleWhen`: "Filament swap (one extruder)", the default, or "Logo as its own part (AMS, tool changer)", where the logo fill is its own part), the relief height (a slider with the document's minimum, maximum and step, hidden for an inlay by its `visibleWhen`) and the margin. A hidden parameter is not sent, so it takes the document's default.
- **Artwork.** The sample chooser offers "NEURALDEEP.NET wordmark", the default because the playground is Neural Deep Network's public demo, "NEURALDEEP.NET wordmark (square)" and "OpenBrick3D sample mark (CC0)" (`parts/assets/mark.svg`, the logo tile's own default). The samples come from the core (`artwork_samples_json()`, which bundles the files with `include_str!`), and each is sent under its asset name in `parts/`, so the CLI and `native_eval` give the same content hash. A sample has a drawing per tile it was drawn for (the wordmark for 2x6, 2x8 and 2x10, the square wordmark for 4x4); the page sends the one drawn for the largest tile that fits the tile being designed, else the smallest (`src/samples.js`). The whole text does not print on a smaller tile, so the playground starts the logo tile at 2x6 with the wordmark. Choosing the square wordmark on a tile that is not square or smaller than 4x4 sets the size to 4x4, and choosing the wordmark on a tile that is not longer than wide or smaller than 2x6 sets 2x6; the note under the chooser and the next status line say so, and later size changes are yours. While a Neuraldeep.net drawing is in use, the first sentence of its notice shows under the drop zone ("Copyright Neural Deep Network Ltd. All rights reserved.", with a "Read the notice" link to [`parts/assets/brand/NOTICE.md`](../../parts/assets/brand/NOTICE.md)): the marks are Neural Deep Network Ltd's trademarks, not under this repository's licences, for building, printing and showing the OpenBrick3D demo tiles only. So a build of this page carries them; a fork that may not ship them removes them from `artwork_samples_json` (see [PACKAGING.md](../../PACKAGING.md)). Your own SVG works as before: drop it on the drop zone or the 3D view, or choose one (the drop zone is a button: click, Enter or Space open the file picker); the chooser then shows "Your SVG" and choosing a sample again replaces it. Files over the core's limit (4 MiB, `max_asset_bytes()`) are refused in the page with a message before anything is sent; the core refuses hostile SVGs with its own messages.
- **Printer.** The process profile (fdm-0.4, fdm-0.2, resin-msla) and the fit profile: the example (Prusa MK4S, PETG; illustrative values, not measured), "Recorded in this browser" (the one the record step wrote, once you use it), "Load my fit profile…" (the JSON file `openbrick calibrate record` or the record step writes), or "None (uncalibrated)". With none, FIT.MISSING blocks the downloads, and both the reason next to them and the finding offer **Calibrate**, which opens the coupon mode's record step, besides the coupon itself and the [print test guide](https://github.com/NeuralDEEPnet/openBrick/blob/main/docs/guides/print-test.md); a fit profile calibrated for another process gives FIT.PROCESS with the same offer. Body and logo colours are pickers; they recolour the view and go into the 3MF. The printer menu (none at first) names a bundled printer from `printers_json()` (Prusa XL with one or five toolheads, Prusa MINI+, Bambu Lab A1 alone or with AMS lite); the core then checks that the tile fits its build volume (SIZE.BED, `evaluate_part_on_printer`, and `export_part_on_printer` refuses a tile that does not), and the coupon mode takes the same printer's bed. The choice stays in this browser (`localStorage`, wrapped like the recorded fit profile); with none, the validation panel says SIZE.BED was not checked.
- **Live 3D.** Every change re-evaluates after 150 ms. The body and the accent object show in their colours, and the artwork that does not print as drawn is drawn in red on the face, always with a legend entry that says how much (percent of the artwork area), so colour is never the only cue. The result lists the triangle count, the size in millimetres and the mass printed solid in PLA. A slow evaluation shows its seconds in the status line; any change cancels it. A reply for controls that changed meanwhile (a newer value, or a field that is now invalid) is dropped, so it can never replace a field's message or turn the downloads back on. When the core refuses to build (a broken fit profile, an SVG it cannot read), the 3D view and the stats empty and the legend, status line and validation panel say why, so nothing on screen describes other controls; the coupon mode does the same with its view, stats and cell table.
- **Validation.** Every finding with an icon and the severity in words, the rule id, the message, the measured value and threshold, and the fix hint; blockers first. The unit after the numbers comes from the core (`openbrick_print::finding_unit`, through `report_units_json()`), never from the wording of the message. After the findings, every rule the core could not check is listed with its reason (SIZE.BED without a printer, TRADEMARK.LOGO on artwork until the Q16 matcher exists), so no rule passes silently. The evaluator's own notes follow (for an inlay, where the filament change goes). Download 3MF and Download STL stay off while any blocker stands, with the reason next to them, and the core refuses such an export too. Files are named `{id}-{w}x{h}-{relief}.3mf`, plus the inlay style for an inlay and the sample for a bundled sample (`neuraldeep`, `neuraldeep-badge` or `sample`; nothing for your own SVG), for example `ndn.logo-tile-2x4-emboss-neuraldeep.3mf`, `ndn.logo-tile-2x4-inlay-parts-neuraldeep.3mf` and `ndn.logo-tile-4x4-emboss-neuraldeep-badge.3mf`, so the two inlay styles never share a name and neither do two samples. The height, the margin and the name of your own SVG are not in the name, so, for example, a plate and a brick tile of the same size, relief and artwork download under the same name. The 3MF is one object whose parts are the colour roles (the part-designer layout, `openbrick_io::ExportLayout::PART_DESIGNER`, which the CLI writes too; see [Q18](../../docs/spikes/q18-slicer-multimaterial-import.md)): Bambu Studio loads it as one object with a part per role, and PrusaSlicer asks whether to load it as one multi-part object. The STL is the kernel's fused union, one solid for a single colour (for a parts inlay, the plain tile without visible artwork). An inlay is exported face down, as it prints, with `openbrick_geom::turn_face_down`, the transform the CLI uses, so both write the same meshes (`crates/openbrick/tests/export_parity.rs`).
- **Calibration coupon, step 1: print it.** Process, pocket layout (cross, cross and diagonal, full), printer and bed size (choosing a printer fills in its bed; typing a size sets the printer to Other); the coupon in 3D, its stats, the cell table (the label on each cell of the first copy and what to record for it), Download coupon 3MF and STL, and how to use it, with the `openbrick calibrate record` line as the command-line alternative to step 2.
- **Calibration coupon, step 2: record my fit** (the calibration wizard, [05 section 4](../../docs/plan/05-3d-printing-pipeline.md#4-calibration-coupon-and-wizard): "tap the cell"). The process, pocket layout and bed above say which coupon was printed. A map of it, built from the core's cell layout (`coupon_layout_json()`; `src/calibration.js` only places those cells for display, with the back edge up so the labels read as printed): both copies, every cell at its printed position in its copy with its embossed label, a stud as a dot, a bore as a ring, a pocket as a square over its two numbers. Copies printed one behind the other (the default) are drawn as printed, outlined and captioned (copy 1 at the back). Copies printed side by side (the full pocket set on a large bed) are drawn one under the other, each under a band naming it (Copy 1 (left), Copy 2 (right)), because side by side they would share the panel's width and the cells would be too small to tap or read; the caption says so. Every tap target is at least 24 px (WCAG 2.2, 2.5.8) on a 320 px wide panel, and each label is sized from its cell (`labelFontMm`) so it is never clipped. Tap the best stud cell, the best tube bore cell and the best pocket, in either copy: that cell is checked, and the others with the same value (its twin in the other copy, the nominal pocket in the other pocket line) are marked as twins, not checked, so each radio group has one checked radio. A pocket is one choice, its tube OD and rib depth together, and only the pockets the chosen layout printed are on the map; changing the layout clears a pocket the new one lacks. Each kind of cell is a radio group: Tab reaches it, the arrow keys, Home and End move and choose. Then the printer (Prusa MINI+, Prusa XL, Bambu Lab A1 or Other with a name), the material (suggestions PLA, PETG, ABS, ASA), the nozzle (it starts at the command line's default, 0.4 mm, and the help under it says to change it for another nozzle; the summary names the nozzle before you save), the slicer, the date (today in your time zone; emptied, it is today again, as on the command line) and notes. Every change asks the core's `record_fit()` (`openbrick_print::record`, exactly as `openbrick calibrate record`: the same id from printer, material and process, the same rounding, the date as given), which answers the profile, its file name and its offsets, shown as a table (chosen cell, nominal, offset with its sign, offset field) before you save, or a refusal that names its field: the message shows next to that field (once you have edited it, or tried to save) or under the map for cells. **Download fit profile** saves the file under `<id>.json`, byte for byte the file the CLI writes for the same choices (`crates/openbrick/tests/record_parity.rs`). **Use this fit profile** selects it in the logo tile's fit select as "Recorded in this browser", moves the tile to the process it was calibrated for (and says so), and keeps it in `localStorage` for this browser only; the next visit starts with it, and the note under the fit select says so when that moved the process. "Forget my recorded fit profile" under the fit select removes it. Every storage access is wrapped (`src/storage.js`): without storage (a private window, blocked site data, a full quota) the profile is used for the open page only and the note says to download it.

URL parameters: `?mode=coupon` opens the coupon, `?mode=coupon&step=record` its record step; `?backend=webgl2` forces the WebGL2 backend (`webgpu` and `auto`, the default, let three.js choose).

## Build mode: a place to play

The **Build** tab is the first playable assembler (docs/plan/07; the alpha on our own generated parts, plus the real LDraw parts from a pack you import: see [Real parts](#real-ldraw-parts)). Open it at `?mode=build`.

**How to play**

1. Pick a part in the palette (bricks, plates, tiles and a baseplate; each thumbnail is drawn from the mesh the part evaluator built) and a colour.
2. Move the pointer over the ground, a baseplate or a part. The translucent ghost is the pose the core snapped to: green where it fits, red where it does not, and the line at the top of the 3D view says why ("would overlap the Plate 1 x 2", "would not connect to anything") and what to do. That line is not a live region, so moving the pointer is silent for a screen reader; a change to a different problem is announced once, in the message under the tools. The whole Y = 0 plane is the table (a model needs no baseplate), and Build mode draws it as a grid of studs, so a ghost on the ground is never over an invisible floor; a baseplate is just a big plate.
3. Click or tap to place. The ghost lands on the studs under the pointer, on the underside of an overhang, beside a part, or on the ground, whichever the pointer ray hits.
4. **R** (Shift+R back) or the *Rotate 90°* button turns the next part. **Delete** or **Backspace** removes the part under the pointer or the aim (outlined in yellow); any part can go, a baseplate too. The *Remove mode* button (no key) turns every click or tap into a removal, which is the way on a phone. **Ctrl or Cmd+Z** undoes, **Ctrl or Cmd+Shift+Z** (or Ctrl+Y) redoes; the buttons do the same. **Escape** leaves remove mode. *Clear* removes every part except the baseplates standing on the ground (a baseplate laid on bricks goes too), and one undo brings it all back.
5. Orbit with a drag (one finger on a phone), zoom with the wheel or a pinch, pan with right-drag or two fingers. A tap or click that barely moves is a placement; a drag is the camera.
6. **Keyboard.** Tab to the 3D view (it shows a focus outline and its name says how to use it). Arrow keys move an aim by one stud, away from you, towards you, left and right as the camera looks; the core snaps the part to the ground point under the aim exactly as it does under a pointer, so you can build anywhere on the table, on top of parts too. **Enter** or **Space** places at the aim (the first press only shows where it is); **Delete** removes the part at the aim. **Shift+arrows** orbit, **+** and **-** zoom, **Home** frames the model. *Place in the middle of the view* is still there for a one-button placement. Beside, under and between parts is by pointer or touch; the keyboard builds on the ground and on tops.
7. **Samples** has a Neuraldeep-blue house (49 parts) and a rainbow staircase. **Save .obrick.json** downloads the model (a native save dialog in the desktop app). The alpha writes the plain JSON `model.json` of docs/plan/08, so the file is `<name>.obrick.json`; the zipped `.obrick` comes later. **Open .obrick.json** reads one back and the core checks every part again (a file that is not a model, or has an id of 0, a position beyond 100,000,000 LDU or an unknown part, is refused with a message and the model stays). Opening a file or a sample while there are edits since the last save asks first, in the page: *Save first*, *Replace* or *Cancel* (Escape cancels; focus starts on Cancel). Afterwards *Restore previous model* brings the replaced one back, and pressing it again swaps them.

The **Model** panel shows the parts, the connections (a stud in a receptacle is one), the connected groups, the parts on the ground and the *floating* ones: parts with no chain of connections to a part on the ground. Floating is a hint, not an error. The bill of materials counts part by colour.

**How it works.** The page never decides where a part goes. It turns the pointer into a ray in the model's frame (LDU) and sends it, with the part and rotation, to the core worker (`asmSnap`); `asmApply` takes a command (add, remove, move, turn, recolour, clear, clear built) and answers with the model's new state: an `Int32Array` of seven numbers per part, the stats and the bill of materials. The scene (`src/assembly-view.js`) is one `InstancedMesh` per part with the colour per instance, so a model is at most 14 draw calls, plus the ghost and the outline. Models above 250 parts use the cheap mesh level (8 segments per stud instead of 24, about 45 percent of the triangles) until they shrink below 150. The pure logic (reading the state, keys, the status texts, thumbnails, file names) is in `src/build.js` with node tests; the controller is `src/build-ui.js`. The worker holds the one model. The page replaces that worker when a slow Part or coupon build is cancelled (src/client.js) and after a trap, and a new worker starts with an empty one, so the page keeps the model's text after every change (the core returns it with the state) and, through `src/model-keeper.js`, puts it back before the next request to a replaced worker, and says so. The undo history lives in the worker and is lost by a restart.

**Performance, measured by the smoke test.** On the shared build machine (Chromium on SwiftShader, so software rendering: it proves the page works, not how fast a device is) a model of 513 bricks (16 layers of 32 bricks of 2 x 4 on the baseplate) opens in about 0.2 s, draws as 2 draw calls and 536,000 triangles, and the core answers a snap query in 0.1 to 0.3 ms, a pick in under 0.2 ms, and a place plus undo in about 2 to 3 ms with the whole model in place. Orbiting it renders at about 5 to 6 frames per second in software; on a GPU that is a small scene (docs/plan/07 section 9 budgets 10 to 20 million triangles per frame on an integrated GPU). The 10,000-part target needs the LOD pipeline and chunked culling that are still to do.

### Real LDraw parts

**Add parts from an LDraw library…** (under the palette) loads an `.obpack` made by `openbrick catalog import` from your own copy of the LDraw Parts Library (docs/guides/ldraw-parts.md: fetch, import, load; licence and attribution). The core checks and loads it (`asmLoadPack`; the page keeps the bytes and sends them again to a replaced worker, before the model), its parts join the catalog after the 13 built-ins and the baseplate (ids `ld.<number>`; part numbers of the built-ins never move), and the palette becomes a searchable, categorised, paged list (24 per page; a search matches words by their start and sizes like `2x4`; thumbnails are drawn on a canvas from the core's meshes for the page on screen only). Parts marked *ground only* have no connector; parts marked *joint not modelled* have a clip, hinge, ball or socket whose studs snap but whose joint does not. The pack's attribution line, counts and licence text show while it is loaded, and each chosen part shows its author and licence line. A model saved with pack parts names the pack (`requires`); opening one without the pack shows what it needs and a button to add it, then opens the model when the pack is in. **Remove the LDraw pack** goes back to the built-ins. In the desktop app the file comes from the native dialog (`pick_file` with kind `pack`, up to 256 MiB).

**Meshes and draw calls with hundreds of part types.** One InstancedMesh per part type in the model, so a model of N different parts is N draw calls however many copies there are; a mesh is uploaded to the GPU only for placed parts and the one being placed, and parts that are neither are released beyond a spare of 32 (`src/parts-list.js` `gpuPlan`); the CPU copies kept for thumbnails are an LRU of 48 beyond the placed ones. `window.__web.build.spread(n)` places n different parts through the core for the smoke test, which prints draw calls, uploaded meshes and frame times when `OPENBRICK_SMOKE_PACK` names a real pack (`node smoke.mjs --no-build --only-pack`).

## Run it

You need the Rust toolchain with the `wasm32-unknown-unknown` target, Node 22, pnpm 10, and the pinned wasm-bindgen CLI. The CLI version must equal the `wasm-bindgen` crate in `Cargo.lock`; `cargo xtask wasm` checks this and prints the install command if it does not match.

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version =0.2.129 --locked   # once; it compiles for a few minutes
pnpm install                                                 # once, from the repository root
pnpm --dir apps/web start                                    # build the core, then serve the app
```

`start` runs `cargo xtask wasm` and then Vite's dev server. Open the printed `Local:` URL (normally http://localhost:5173/). After that:

```sh
pnpm --dir apps/web dev        # serve again without rebuilding the core
pnpm --dir apps/web wasm       # rebuild the core after a Rust change (Vite reloads the page)
pnpm --dir apps/web build      # production build into dist/
pnpm --dir apps/web preview    # serve dist/
pnpm --dir apps/web test       # unit tests (node --test); the root pnpm test runs them too
pnpm --dir apps/web smoke      # build everything and check it in headless Chromium
OPENBRICK_BASE=/openBrick/ pnpm --dir apps/web build   # the GitHub Pages build
```

`OPENBRICK_BASE` is the path the app is served under, `/` by default. The page, the worker, the WebAssembly module and every asset resolve under it.

`cargo xtask wasm` builds `crates/openbrick-wasm` in release for `wasm32-unknown-unknown`. It then runs `wasm-bindgen --target web` into `src/wasm/`, which is generated and gitignored, and prints the module size. It fails if the gzipped module exceeds the 2.5 MB budget in [10 section 5](../../docs/plan/10-repo-layout-and-dev-tooling.md#5-ci-matrix). With the evaluator, usvg, the validator, the coupon, the calibration record (`record_fit`), opening and saving part documents, the 3MF and STL writers and the bundled artwork (the four Neuraldeep.net drawings add about 42 KB of SVG text) linked, the module is 3,389,614 bytes raw and 1,118,530 bytes gzipped (flate2 at its best compression), 45 percent of the budget; the self-intersection and overhang analyses and the printer profiles added about 44 KB gzipped, and opening and saving part documents about 35 KB.

The footer carries the non-affiliation disclaimer ([12 section 4](../../docs/plan/12-legal-and-naming.md#4-disclaimer-text)) from `crates/openbrick-units/disclaimer.txt`, the one file the CLI's `openbrick about` and the core's `disclaimer()` also read; `vite.config.js` writes it into the HTML. After it come the links to the documentation site and to the source code.

### On a phone on the same network

```sh
pnpm --dir apps/web start --host      # or, with the core already built: pnpm --dir apps/web dev --host
```

Vite prints a `Network:` URL such as `http://192.168.1.20:5173/`. Open it on the phone, which must be on the same Wi-Fi. If the page does not load, allow port 5173 through the computer's firewall. The 3D view is on top and the controls scroll below it. One finger orbits, two fingers pinch to zoom and pan, and the + and - buttons are 40 px touch targets. The orbit goes all the way round: drag up to look at the underside (the tubes). While the camera is below the ground, the grid and the contact shadow hide.

Browsers expose WebGPU only in secure contexts, and `http://192.168.1.20:5173/` is not one, so a phone on plain HTTP renders with WebGL2. To try WebGPU on a phone, use `adb reverse tcp:5173 tcp:5173` and http://localhost:5173/ on Android. Or serve HTTPS with a locally trusted certificate made with [mkcert](https://github.com/FiloSottile/mkcert), kept outside the repository:

```sh
WEB_TLS_CERT="$HOME"/.config/openbrick-harness/192.168.1.20.pem \
WEB_TLS_KEY="$HOME"/.config/openbrick-harness/192.168.1.20-key.pem \
pnpm --dir apps/web dev --host
```

[`bench/devices/README.md`](../../bench/devices/README.md#run-it-on-a-phone-on-the-same-network) describes how to make the certificate and trust it on the phone.

## How it fits together

```text
main thread                                   Web Worker (src/worker.js)
-----------                                   --------------------------
compile openbrick_wasm_bg.wasm once
CoreClient (src/client.js) --- init(module) ---> instantiate the core
                           --- bundled ---------> profiles, part document, samples, disclaimer
                           --- evaluatePart ----> evaluate_part[_on_printer](doc, params, process, fit, assets[, printer])
                           --- exportPart ------> export_part(format, ...)  -> 3MF or STL bytes
                           --- buildCoupon -----> build_coupon(process, layout)
                           --- couponLayout ----> coupon_layout_json(process, layout) (the record step's map)
                           --- exportCoupon ----> export_coupon(format, ...)
```

### Messages

Every request carries an `id`, and the worker answers each one with `{ id, ok: true, result }` or `{ id, ok: false, error }`. The error reply also has `fatal: true` when the core trapped (a WebAssembly `RuntimeError`, which is how a Rust panic ends on wasm32). `src/protocol.js` lists every message and its fields: `init`, `info`, `bundled`, `brick`, `checkPart`, `evaluatePart`, `exportPart`, `resolveParams`, `buildCoupon`, `couponLayout`, `exportCoupon`, `recordFit`, `openPart`, `savePart` and `addPreset` (protocol version 4). A refusal of `recordFit` is an answer (`{ ok: false, error: { field, message } }`), not a failed request, and so is a file `openPart` refuses (`{ ok: false, error }`). Mesh arrays and file bytes in results are transferred, not copied. Asset bytes in requests are copied by `postMessage`, because the page keeps them to send them again to a replacement worker.

A running WebAssembly call cannot be interrupted. Builds (`brick`, `evaluatePart`, `buildCoupon`) are therefore "latest wins": a new one replaces any build still waiting. If the build in progress has run for 250 ms, the client terminates the worker and starts a new one from the already compiled module. In Node on the shared build machine the default 2x4 tile takes about 110 ms in WebAssembly, a 16x16 tile 2.2 s and the default coupon 0.55 s, so changing a 16x16 back to 2x4 shows the small tile at once. Exports (`exportPart`, `exportCoupon`) are never superseded: while one is owed, the client does not restart the worker, and it cancels a superseded build only after the export has its reply.

After a trap, the instance's memory may be inconsistent. The worker therefore refuses every later request, and the client replaces it at once with a fresh worker from the same compiled module. The fresh worker also receives every request the old one still owed, exports included, with the original ids. The request that trapped fails with the error, and the page shows it.

### Frames

The core returns millimetres in the kernel frame: right-handed, +Z up, with the body's minimum corner at the origin. three.js is right-handed with +Y up. The part lives in a group rotated by -90 degrees about +X, which maps (x, y, z) to (x, z, -y). The determinant is +1, so triangle winding and back-face culling are unchanged, and one three.js unit is one millimetre. This conversion is `packages/viewport/src/frame.js`, the same module the render harness uses. Inside that group, a tile is moved so that its lattice cell corner lies on a grid line (`src/placement.js`), using the pitch and undersize the core reports from the Dimensional Standard; the coupon is centred. The grid has one cell per stud.
